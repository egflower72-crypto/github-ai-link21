# 2026-11-26 매일 설계 — calcom/cal.diy (상담 예약)

## 한 줄 결론

**보류 — 지금은 만들지 않는다. 상담 예약은 일반 도구(캘린더의 예약 기능, 설문 폼)로 한다.** 원본을 그대로 설치하는 것도 권하지 않는다. 원본이 스스로 「개인용 · 비운영용」이라고 적었고, 고친 판이 표시되지 않은 공개 보안 권고가 남아 있다. 직접 만드는 안은 일반 도구보다 더 줄여 주는 시간이 0에 가깝고(추정), 알림과 캘린더 겹침 확인이 빠져 오히려 기능이 적다. 일반 도구를 2주 써 보고 「부족한 점」이 글로 남을 때만 다시 올린다. 아래 「가장 작은 완성판」은 그때 쓸 참고안이다.

## 무엇을 하는 도구인가

1. 「30분 상담」 같은 예약 종류를 만들고, 받을 수 있는 요일 · 시간을 정해 두면 공개 예약 주소가 생긴다.
2. 손님이 그 주소에서 빈 시간을 골라 이름 · 연락처를 넣으면 예약이 잡히고, 양쪽에 확인 메일이 간다. 구글 · 아웃룩 캘린더와 겹치는 시간은 자동으로 막는다.
3. Cal.com의 유료 기능(팀, 조직, 자동 알림 흐름, 통계)을 뺀 공개판이다. 운영사가 대신 돌려 주는 서비스는 없고, 직접 서버에 올려야 한다.

## 링크21의 어떤 일을 줄이는가

- 대상 업무: 수강 문의가 왔을 때 상담 시간을 잡는 일.
- 지금 방식: 메신저 · 전화로 「언제 되세요?」를 주고받고, 정해진 시간을 스프레드시트와 캘린더에 손으로 적는다.
- 바뀐 방식: 모집 글에 예약 주소를 붙인다. 문의자가 빈 시간을 직접 고르고, 예약 목록이 자동으로 쌓인다.
- 주당 절약 시간(추정): 약 40분. 가정: 상담 예약 주 10건, 건당 시간 조율에 5분 → 예약 화면이 있으면 확인만 1분.
- **일반 도구와 견준 값(추정): 추가 절약은 0에 가깝다.** 캘린더에 들어 있는 예약 기능이나 설문 폼으로도 「빈 시간 직접 고르기」는 된다. 직접 만들어 더 얻는 것은 「상담 종류 · 과정별로 예약 목록이 한 표에 모이는 것」 정도다.
- 위 40분에는 만드는 시간과 만든 뒤 고치는 시간이 들어 있지 않다. 건수(주 10건)와 건당 5분은 재 본 값이 아니라 가정이다. 문의자가 예약 주소 대신 메신저 · 전화로 계속 묻는다면 절약은 더 작아진다.
- 실제 주당 상담 건수는 이 문서에 넣지 않았다(공개 저장소). 대표가 실제 건수로 위 계산을 다시 해 보면 된다.

## 원본에 비개발자용 설치 방법이 있는가

- 있다. README에 Railway · Northflank · Render · Elestio 「누르면 배포」 단추와 Docker 설치 순서가 있다. Vercel은 유료(Pro) 요금제가 필요하다고 적혀 있다.
- 그러나 README 첫 줄이 이렇게 경고한다: 「개인용 · 비운영용으로만 강하게 권장. 직접 호스팅은 서버 · 데이터베이스 · 보안 지식이 필요」. 상업 · 운영용은 유료 Cal.com을 쓰라고 안내한다.
- 배포 단추가 Cal.diy 최신판을 올리는지는 확인 불가다. Render 단추는 다른 저장소(`calcom/docker`)를 가리킨다.
- 정리: 「설치해서 써 보면 된다」가 가능은 하지만, 외부 사람의 연락처를 받는 용도로는 원본 스스로 권하지 않는다.

## 구조 (원본)

- 프론트: Next.js + React + Tailwind. `apps/web`에 공개 예약 화면과 관리 화면이 함께 있다. 한국어 번역 파일은 `packages/i18n/locales/ko`에 들어 있다.
- 백엔드: 같은 Next.js 서버 안의 tRPC (`packages/trpc/server/routers/viewer` — eventTypes, availability, slots, bookings, calendars, webhook 등). 별도 REST 서버 `apps/api/v2`(NestJS)가 있다.
- 핵심 모듈: 빈 시간 계산 `packages/features/slots` · `availability` · `busyTimes`, 예약 생성 `packages/features/bookings/lib`, 메일 `packages/emails`, 연동 앱 `packages/app-store`.
- 데이터베이스: PostgreSQL + Prisma. `packages/prisma/schema.prisma`에 모델 100개. Docker 구성에는 Redis도 들어 있다.

| 테이블 | 주요 컬럼 | 뜻 |
|---|---|---|
| User | id, email, username, timeZone, defaultScheduleId | 상담을 받는 직원 |
| EventType | id, title, slug, length(분), userId, bookingFields, requiresConfirmation | 예약 종류 |
| Schedule | id, userId, name, timeZone | 근무 시간표 묶음 |
| Availability | id, scheduleId, days, startTime, endTime, date | 요일별 가능 시간, 특정 날짜 예외 |
| Booking | id, uid, eventTypeId, userId, startTime, endTime, status, responses, cancellationReason | 예약 한 건 |
| Attendee | id, bookingId, name, email, phoneNumber, noShow | 예약한 사람 |
| Credential · SelectedCalendar | type, key, userId · integration, externalId | 캘린더 연동 정보 |
| Webhook | id, subscriberUrl, eventTriggers, userId, teamId | 예약 발생 시 외부 알림 |

- 외부 연동: 구글 캘린더, 마이크로소프트, Zoom, Daily 등. 각각 개발자 계정에서 키를 발급받아야 한다(README 「Integrations」).

## 가장 작은 완성판 범위 (대표가 「만든다」로 고를 때만)

원본을 올리지 않는다. 표 구조 4개(EventType, Availability, Booking, Attendee)의 생각만 빌려 작게 새로 만든다.

화면 목록
1. 공개 예약 화면: 상담 종류 고르기 → 빈 시간 고르기 → 이름 · 연락처 · 관심 과정 입력 → 완료.
2. 예약 확인 · 취소 화면(예약자용, 예약별 고유 주소).
3. 관리자: 상담 종류 관리.
4. 관리자: 가능 요일 · 시간 설정.
5. 관리자: 예약 목록(날짜 · 상태로 거르기, 「왔음 / 안 왔음」 표시).

API 목록
- `GET /api/slots?type=&date=` 빈 시간 조회
- `POST /api/bookings` 예약 생성(같은 시간 중복 막기)
- `GET /api/bookings/:uid`, `POST /api/bookings/:uid/cancel`
- `GET·POST·PATCH /api/admin/consult-types`
- `GET·PUT /api/admin/availability`
- `GET /api/admin/bookings`, `PATCH /api/admin/bookings/:id`

데이터베이스(4개 표)
- `consult_types`(id, title, slug, length_min, active)
- `availability`(id, weekday, start_time, end_time, date_override)
- `bookings`(id, uid, consult_type_id, start_at, end_at, status, cancel_reason, created_at)
- `attendees`(id, booking_id, name, phone, email, interest_course, consent_at)

만들지 않을 것: 캘린더 연동, 결제, 화상회의 연결, 팀 · 권한, 웹훅, 분석 코드 삽입칸, 문자 · 알림톡 자동 발송(발송은 건별 승인 대상), 원본 코드 복사.

이 범위의 한계(검수에서 덧붙임)
- 알림이 없다. 예약이 들어와도 직원은 관리자 화면을 열어 봐야 알고, 예약자는 완료 화면의 주소를 따로 적어 두어야 취소할 수 있다. 일반 캘린더 예약 기능은 확인 메일과 일정 등록이 자동이다.
- 캘린더 연동이 없다. 강의 · 외근과 겹치는 시간은 직원이 가능 시간을 손으로 고쳐 막아야 한다.
- 위 목록에 아직 없는 것: 관리자 로그인 방식과 계정 저장 위치, 공개 예약 API의 도배 · 자동 입력 막기, 보관 기간이 지난 연락처를 지우는 기능. 넣으면 화면 5개 · 표 4개보다 커진다.

## 위험

- 개인정보: 수강 희망자의 이름 · 연락처를 받는다. 수집 동의 문구, 보관 기간, 삭제 방법이 먼저 정해져야 한다. 원본을 그대로 올리면 위 권고(예약 정보 유출, 악성 스크립트)가 고쳐졌는지 확인하지 못한 채로 연락처를 쌓게 된다. 직접 만든 판도 연락처가 든 DB를 인터넷에 열어 두는 것이라, 접근 통제 · 암호화 · 파기 같은 안전 조치를 회사가 직접 져야 한다(법에서 요구하는 구체 항목은 확인하지 않았다. 전문가 확인 필요).
- 비용: 원본은 서버 + PostgreSQL + Redis가 계속 켜져 있어야 한다. 금액은 확인 불가(호스팅 업체별로 다름). 작은 자체판은 서버 1개 + DB 1개면 된다.
- 유지보수: 원본은 9개월째 새 릴리스가 없고 30일 커밋 15개가 대부분 정리와 작은 수정이다. 보안 수정 PR이 두 달 넘게 병합되지 않았다. 모델 100개짜리 큰 코드라 비개발자 팀이 직접 고칠 수 없다. 자체판도 만든 뒤 고쳐 줄 사람이 필요하다.
- 라이선스: MIT라 걸리는 것은 없다. 코드를 복사하면 저작권 표시를 남겨야 한다. `apps/api/v2`는 표시가 달라 쓰지 않는다.
- 가장 큰 위험: 일반 도구로 이미 되는 일을 다시 만드는 것.
